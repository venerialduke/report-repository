Insights Hub plan: one home for every analysis, prototyped on GitHub Pages and headed for Databricks

What the Hub is for, what works today, the decisions we have made, and how it moves to a Databricks App with team-only and company-wide spaces.

By Insights Hub working group Published Sep 23, 2026 Status Living plan, updated as decisions land

The short version

  1. The prototype is live. Reports are plain HTML files in git, and GitHub Pages serves them. The site has discovery, full-text search, area pages, a report viewer, PDF export, AI summaries, chart downloads, shared brand assets and Claude skills.
  2. Reports stay simple: a folder with index.html and report.json, relative links, and charts written as JSON. That keeps them portable from git to GitHub Pages to Databricks without edits.
  3. The destination is a Databricks App. It brings single sign-on, and each audience's reports sit in their own Unity Catalog Volume: team (Insights only), org (everyone) and later restricted spaces. Promotion is one field change.
  4. We keep it static for now. Charts embed their data; there are no live queries. Published reports can be frozen into self-contained snapshots so later asset changes can't break them.
  5. First decision needed: confirm that business readers can access a Databricks App. That decides whether the Hub can reach its whole audience there.

01Goals: make every analysis findable, trustworthy and reusable

Insights work is scattered across emails, drives and notebooks. The Hub gives it one address and one standard.

DiscoverAnyone can find the analysis that answers their question, by area, topic, owner or anything in the text.
TrustEvery report carries its owners, date, status, data sources and code links, so readers know how current and how solid it is.
ConsistencyShared brand, templates, chart library and review skills make reports look and read like one team produced them.
LeverageAI summaries, cross-report synthesis, PDF bundles and chart downloads help readers act on the work, not just read it.
ControlPublish privately to the team first, then promote to the company, with access enforced by the platform.

03How it works today: git is the source of truth and GitHub Pages serves main

Publishing is a pull request. Nothing runs on a server; every feature runs in the reader's browser.

Prototype limitation

GitHub Pages sites are public. That's fine for fictional sample content, but real reports need the private hosting in section 04.

04Where it's going: a Databricks App, with Unity Catalog deciding who sees what

Same reports, same front end. The app adds company login, and Unity Catalog permissions decide who can see which reports.

How it works

  • Storage: each Volume mirrors the repo layout (reports/<id>/…, catalog.json). Shared brand files ship with the app. Relative links resolve the same way in git, on GitHub Pages and in Databricks.
  • Visibility: a "visibility": "team" | "org" field in report.json. CI syncs each report to the matching Volume and removes it from the others. New reports default to team.
  • Promotion: a one-line pull request (team → org), with review and an audit trail. Demotion is the reverse. A Promote button in the app can come later.
  • Access: the app reads Volumes as the signed-in user, so Unity Catalog grants decide what each person sees in listings, search, area pages, AI and file access. A link to a report someone can't see shows a neutral "not available".
  • AI and comments: AI calls go to a Databricks model serving endpoint, so readers no longer need their own keys. Comments go in a table, keyed to the reader's company login.
Checks before a report is promoted to org

No links to team-only reports or assets · status is final · metadata complete · embedded data is aggregated and suitable for everyone who can see org (a reviewer checklist item).

05Decisions so far: static reports, snapshots for durability, one catalog

DecisionChoiceWhy
Report formatPlain HTML folder + report.json, relative links, charts as JSONPortable across hosts. Search, AI and CSV downloads can all read the chart data.
Report dataEmbedded (static) only, for nowNo query engine, per-user caching or permission-aware SQL to build. Live data can come later if needed.
Shared assetsAuthor against shared assets, publish a frozen snapshotReuse while writing; published reports can't break when a shared asset changes.
AudiencesOne catalog and schema (insights.hub), one Volume per audienceVolume grants are enough when there is no live data. Separate catalogs would add governance overhead for no gain.
Status vs visibilityTwo separate fieldsQuality (draft/final) and audience (team/org) change independently.
Source of truthGit, private to the Insights teamReview, history and CI checks come for free. The repo holds team-only drafts, so repo access must stay limited.

Snapshots: self-contained published copies

A npm run snapshot script plus a report-snapshot Claude skill will turn a report into one self-contained HTML file:

  • styles inlined;
  • charts pre-rendered to SVG, with their JSON kept so CSV downloads still work;
  • images compressed and embedded, fonts subset or replaced with system fonts;
  • a size budget (warn at 2 MB, fail at 5 MB);
  • a stamp with the snapshot date and source commit;
  • a check that it loads with the network blocked.

CI snapshots on publish or promotion, and re-snapshots every report that references a shared asset before that asset changes.

06Roadmap: finish the prototype, then move in three steps

  1. Prototype on GitHub Pages Done

    All features in section 02, 22 sample reports and articles, 5 Claude skills, CI and the refresh workflow.

  2. Prototype polish Next

    • visibility field (validated and shown as a badge), and a CI check for links to team-only content.
    • Snapshot script, the report-snapshot skill, and a size budget.
    • Turn on giscus comments; add an ANTHROPIC_API_KEY secret for pre-generated summaries.
    • Folder conventions: shared/assets/ for reusable assets and assets/ in each report folder.

  3. Databricks step 1: lift and shift

    A small app (e.g. FastAPI) serves the current site behind company login. Reports are private immediately, with almost no front-end changes.

  4. Databricks step 2: swap the backends

    AI moves to a model serving endpoint (the Hub already supports a proxy URL for this), and comments move to a table. Readers no longer need their own API keys.

  5. Databricks step 3: Volumes and promotion

    Team, org and later restricted Volumes; CI sync driven by the visibility field; per-user catalog; neutral "not available" pages; snapshots published to the Volumes.

  6. Later

    • View analytics and a "most read" carousel
    • Semantic search
    • Links from data sources to Unity Catalog lineage
    • Per-area subscriptions
    • Optionally, live charts from Delta views, queried as the reader
